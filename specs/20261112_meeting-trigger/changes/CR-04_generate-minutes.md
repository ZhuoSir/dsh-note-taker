# CR-04 历史纪要里「待生成」的会议要能给生成按钮

## §S 需求变更

### 触发

用户 2026-11-12 反馈（原话）：

> 待生成的，没有生成纪要的操作按钮

追问「按钮背后的生成方式」时，用户明确指示（原话）：

> 生成纪要，就和正常逻辑一样，发给会话生成

### 判断

CR-03 把历史纪要搬到页面里了，但只做到「能看」，**没有「能生成」**：
列表里 `仅转写` 那几行点开只有转写正文，用户想让它变成纪要只能绕去会话里说话。

生成方式**不走 `POST /minutes`**：用户要的是「和正常逻辑一样，发给会话生成」——
即把该会议的转写组成会记消息，发到当前打开的会话，由会话里的 agent 生成纪要并写回产物。
这与确认区里「交给会话生成纪要」是同一条链路（同一个 `buildHandoffMessage` + `deliver`），
因此不会出现两套纪要口径。

### 条款变更

| 条款 | 处置 | 说明 |
|---|---|---|
| R-15 历史纪要列表 | 改 | 每行在 `transcribe=done && minutes!=done` 时 SHALL 提供「生成纪要」按钮 |
| R-16 纪要生成动作（新增） | 增 | 点击 SHALL 取该场转写 → 组成会记消息 → 发到当前会话；期间禁止重复点击；成功给出目标会话 id，失败就地说明原因 |
| CR-03 §S 边界 | 改 | 「本次不做生成按钮」一条作废 |

### 边界（本次不做）

- 不做「重新生成」（已生成纪要的行不显示按钮，避免「点了会不会覆盖」的顾虑）；
- 不做批量生成、不做生成进度百分比（只有可点/发送中/不可点三态）；
- 识别失败、无转写、录音中断的会议按钮置灰并说明原因，不在此处补做「重试识别」。

## §P 方案

```
历史纪要行
├─ transcribe=done && minutes!=done   → [生成纪要] 可点
├─ transcribe=pending/running         → [生成纪要] 置灰，title=「等识别完成后才能生成」
├─ transcribe=failed                  → [生成纪要] 置灰，title=「识别失败，先重试识别」
├─ record=interrupted                 → [生成纪要] 置灰，title=「录音中断，没有转写」
└─ minutes=done / hasMinutes          → 不渲染按钮
```

点击后：

1. `generatingId = row.id` → 该行按钮变「发送中…」并 disabled，**其他行也一起禁用**（防并发）；
2. `GET /detail` 取该场转写（空则报「这场会议还没有转写，先识别再生成纪要」）；
3. `buildHandoffMessage({ meetingId, label, durationSec, outputPath, transcript })` 组消息；
4. `deliver(text)` → `sendToSession()` 发到 `sessionId ?? currentSessionId()`；
5. 成功：提示「已发送到会话 …xxxxxxxx（全文/摘要，N 字）· 点左侧该会话查看」；
6. 失败：行内红字给出真实原因（写锁被占如实说明），并兜底复制到剪贴板。

实现落点：

- `HistoryList.jsx`：`minutesAction(row)` 判定三态、行内按钮（`stopPropagation`，不触发展开）；
- `QuickPanel.jsx`：抽 `deliver()`（确认区交接与历史生成共用）、新增 `generateMinutes(row)` 与 `generatingId`；
- 服务端与路由不动。
