## 明细

### BL-01 DSH 插件化页面管理

- 意图: 用户最初要求「要有 dsh 插件化的页面管理」，后为先把基本链路跑通而移出本版。
  目标形态是设置区里的「会记」页面（`settings.section` 插槽）+ 会话输入框旁快捷入口
  （`conversation.input.right`），列表可看会议、详情可看转写与纪要、能发起录音与转写并回显状态。
- 立项前必答: 用哪个插槽（已实测在用：`settings.section` / `conversation.input.right` /
  `tool.call.toolview`）；页面数据走宿主侧 HTTP 路由（`ctx.webServer.register`，`kind:'exact'`）
  还是复用工具；是否需要客户端构建链（React 18 + 打包产物 `lib/client.js`）。
- 技术预判: 会引入「共享面」（HTTP 路径）——立项时 plan 必须补身份矩阵；`package.json` 需新增
  `dsh.client` 段与 `./client` 导出，构建链是主要工作量。

### BL-02 音色分人

- 意图: 让纪要能区分「谁说的」，而不只是一堆文字。
- 立项前必答: Python 3.12 独立运行时方案是否接受（sherpa-onnx 在 3.14 不可用，见 L-01）；
  没有真实多人音频时如何定验收标准（见 L-04）。
- 技术预判: 切分 + CAM++ + 聚类的模型已下载在旧数据目录，可复用；工作量集中在运行时与段落对齐。

### BL-03 系统声 / loopback 录音

- 意图: 线上会议里对方的声音也要进录音，否则只有自己一半。
- 立项前必答: 双轨（mic + system）后如何合并成一条带说话人区分的转录。
- 技术预判: `soundcard` 支持 loopback；与 BL-02 有依赖关系（分轨天然区分「我/对方」）。

### BL-04 长会议分块

- 意图: 1 小时以上的会议不把内存吃穿（本机可用内存 3.1–3.3 GB）。
- 立项前必答: 分块边界与时间戳偏移怎么记；块间上下文丢失对纪要质量的影响是否可接受。
- 技术预判: 录音按 10 分钟 rollover + manifest 记偏移；转写逐块串行、合并时累加偏移。

### BL-05 流式 ASR 通道复活（已并入 BL-06）

- 意图: 原本是为「工作空间开通流式模型后，能把已退役的 WS 客户端捡回来」留的口子。
- 现状: 用户 2026-11-10 提出更完整的目标（BL-06：流式上传音频 + 流式 ASR），
  BL-05 作为其中的「协议与客户端」前提并入，不再单独立项。

### BL-06 流式上传音频 + 流式 ASR

- 意图: 开会时就能看到字在长，而不是散会后等几分钟整段识别。同时把「上传」从
  「给一个路径」变成「音频在传」——对超长会议和实时纠错都更友好。
- 来源: 陈卓 2026-11-10 对话「支持 stream 式上传音频，用 stream 的 asr 模型」。
- 立项前必答:
  1. **模型是否可用**：当年该工作空间只有非流式 `qwen-audio-3.0-asr-flash`，
     `-asr-flash-streaming` 不存在（见 CR-01 的 6 组对照实验）。开工前必须重新确认模型可用性，
     否则整条链路无意义。
  2. **音频怎么流**：录音在 Python sidecar（sounddevice），有两条路——
     ① sidecar 边录边吐 PCM → Node 读 → WS 推给云端；
     ② 改由浏览器 MediaRecorder 采集直推。前者改动小但多一跳，后者端到端更短但要重做采集。
  3. **结果怎么合**：流式出的是中间结果（可能改写），需定义「最终以哪一版为准」，
     以及与现有「停录后整段识别 + 人工确认 + 交会话」流程的衔接点。
  4. **成本**：流式按时长计费，与非流式分片按量计费要对比，说明什么场景用哪个。
- 技术预判:
  - WS 协议实现已存在于 commit `2237b86`（含 `run-task`/`task-started`/二进制帧/`finish-task`），
    当时卡在「该工作空间无流式后端」，协议本身是照着文档写的，可复活。
  - 关键工作量在音频通路与 UI 实时渲染，不在协议本身。
  - **可选准流式方案**：模型不支持流式时，用「边录边每 30 秒切一片送非流式接口」做出接近的体验，
    代价是句子边界可能被切开。建议作为降级路线写进方案，而不是等到时再想。
  - 与 BL-04（长会议分块）有交集：分块的边界与偏移逻辑可以复用。

**BL-02 交付说明（2026-11-11 关闭）**

- 目标「区分发言人」已由云端路径实现：`speaker_diarization_enabled` + `qwen-audio-3.1-asr-flash`，
  产物里输出 `S0：`/`S1：`，JSON segments 带 `speakerId`。
- 实测：2 分钟双人样本 → S0 7 句 / S1 40 句；47 分钟全片可跑通。
- 口径边界：分人**只在云端引擎可用**，本机 faster-whisper 不产出发言人；短插话归属不稳定。
- 用户 2026-11-11 决定：云端够用，**本地方案不做**（原计划需要独立 Python 3.12 + sherpa-onnx，
  见 L-01，成本与收益不匹配）。
- 若将来需要离线/免费分人，另开新待办，不复用 BL-02。

### BL-08 已生成纪要可重新生成

- 意图: CR-04 加了「生成纪要」按钮，但只对**还没生成**的会议开放（已有纪要的行不渲染按钮，
  当时的理由是「免得用户担心点了会覆盖」）。用户 2026-11-12 明确要求：已生成的也要能重新生成。
- 现状可直接复用: 服务端 `POST /note-taker/minutes` 已带 `force` 参数；
  MCP `meeting_minutes` 也有 `force`。缺的只是界面入口与确认交互。
- 立项前必答:
  1. 重新生成是**覆盖** `## 纪要` 还是保留历史版本（如 `## 纪要（v2）`）？
  2. 走会话生成还是直接调插件模型——CR-04 已定为「发到当前会话」，重生成是否沿用？
  3. 需不需要二次确认（覆盖属于破坏性操作）？

### BL-09 关键词与关键人员姓名表

- 意图: 会记现在的转写只靠模型裸听，人名、项目名、内部缩写经常听错（例如把姓名听成同音字），
  纪要里的行动项就落不到具体人。用户要一份自己可维护的**关键词 + 关键人员姓名**清单，
  在「转写」和「生成纪要」两个环节都起作用，让纪要理解得对。
- 两处生效点（待定）:
  1. **转写侧热词偏置**：本地 faster-whisper 支持 `initial_prompt`，云端 qwen-asr 支持热词表；
     接哪个、怎么给，立项时定。
  2. **纪要侧上下文**：交接消息里附一段「人名与职责/项目名对照」，让会话里的 agent
     知道「张三 = 项目负责人」「信创 = 信息技术应用创新」这类对应关系。
- 立项前必答:
  1. 清单存哪里：数据目录 `~/.dsh/note-taker/glossary.json`（全局）/ 工作区级 / 单场会议单独给？
  2. 作用范围：全局生效还是按工作区隔离（不同项目的专有名词差别大）？
  3. 结构：只放词，还是「词 ↔ 说明/职责」两列（后者信息量大，但维护成本高）？
  4. 隐私：真实姓名与职责会落盘，是否需要默认不入库（`~/.dsh` 已在 git 外）？
  5. 与 ASR 引擎的关系：本地/云端两条路径都要支持，还是先做一条？
- 与既有账目的关系: 与 BL-02（音色分人）互补——BL-02 解决「谁在说」，本项解决「说的名字对不对」。
