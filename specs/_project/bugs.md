## 证据（实测，2026-11-11 13:19 用户真机）

用户原话：
> 「我刚才测试了一下，正常录制没有问题，但是录制中，不能对话这个就出问题了，要可以继续对话，
> 而且录制中切换到了其他会话窗口，这个是不是会转到后台，如果当前会话是新建的会话，录制中，
> 那我切到其他会话这个录制会话就不存在了。那就找不回来了，而且其他会话也无法输入内容」

实测数据：

```
$ meeting_list（最近一条）
id: 20261111-1319-bf3a
startedAt: 2026-11-11T05:19:27Z（本地 13:19:27）
endedAt: null        ← 从未收尾
status.record: running
audio: null          ← 音频元数据没落库
stats: null

$ 磁盘上的文件
20261111-1319-bf3a.wav  2470444 字节  LastWrite 13:20:45（≈78 秒）
20261111-1319-bf3a.pcm  2470400 字节  LastWrite 13:20:45

$ Get-CimInstance Win32_Process（python 进程）
（空）                ← record.py 已不在，但账上仍是 running
```

结论：录音进程确实退出过，但**没有任何收尾路径**把 `record` 从 running 翻成 done/interrupted，
音频文件留在磁盘、会议却停在 running，用户界面上也就「找不回来」。

## 根因假设（待方案阶段验证）

| # | 假设 | 证据 | 待验证 |
|---|---|---|---|
| 1 | `recording` 是宿主侧**全局单例**（`lib/service.js:174` 起，`if (recording) return E_STATE`），而停止按钮只挂在发起录音那个会话的卡片里；切走即失去唯一手柄，且别的会话再点开始会被全局单例拒绝 | `service.js` 的 `recording` 模块级变量；`routes.js:259` 只在卡片发起时传 sessionId | 切会话后卡片 phase 变 idle（组件重挂载），但服务端仍在录 |
| 2 | 浏览器刷新/应用退出会杀掉 spawn 出来的 record.py，宿主没有「启动时收割 running」的自愈逻辑 | 上面的进程与账目实测 | 无 |
| 3 | 「其它会话无法输入」可能是卡片覆盖输入区，也可能是宿主输入在录音期间被占用 | 未复现 | 需要用户描述：输入框在不在、能不能点进去、打字有没有字、回车有没有反应 |

## 处置走向（待用户点头再写 requirements）

合并成一个 spec（暂名 `20261112_recording-decouple`），覆盖：

- 录音与会话解耦：录制状态在**任意会话**的入口上都可见（计时常驻），任一处都能停止
- 录制中不阻塞对话：卡片不得覆盖/拦截输入区，录制中可正常收发消息
- 切会话/新建会话丢弃不丢录音：可从未保存会话切走，录音仍可从入口或「设置 → 会记」找回并收尾
- 自愈：宿主启动或下次访问时，把「账上 running 但无子进程」的会议判为「录音中断」并可收尾/丢弃

## 根因更正（2026-11-11 晚）

BUG-01 / BUG-03 的「卡片遮挡输入区」判断**错误**。真机用两段控制台脚本取到了硬证据：

- `document.elementFromPoint(输入框中心)` 命中的就是输入框自己（`DIV._6VeeGW_input`）→ **没有遮挡**
- 点完之后 `document.activeElement` 就是输入框 → **焦点进得去**
- 6 秒监听期间 `focusin` 有、`keydown` 有且 `defaultPrevented=false`、DOM 节点未重建 → **事件既没被拦，也没被重渲染打断**
- 对照实验：卡片收起能输入；**卡片展开但没录音也能输入**；只有「录音开始之后」不能输入

结论：**卡片的几何位置不是原因**（T-08 的锚点修正仍然是对的，但没治好这个 bug）。
真正的触发点是开始录音时那句原生 `window.confirm`（流式识别二次确认）——Electron 里
原生模态会打断渲染进程的输入法编辑上下文，之后输入框收得到 keydown 却输不进字，
缩放窗口重建渲染树才恢复。这与「停止录制后仍卡」「其他会话也不能输入」「缩放恢复」全部吻合。

修法：`window.confirm` 全部换成卡片内的确认条（`askConsent/answerConsent`），
不再调用任何原生对话框。见 commit `fix(client): 去掉原生 confirm，改卡片内确认`。

## BUG-05 证据与定位（2026-11-12）

用户原话：

> 有个 Bug，手动操作生成纪要转发给会话，内容只有第一条一句，没有后面的内容，
> 也没有将 md 文件发给会话，所以总结不出来内容

### 实测（`buildHandoffMessage` 三种配置实跑，非推测）

```
=== 长会议 + 有产物（20261112-1309-2625，转写 24913 字）===
mode=file 消息总长=288
消息前 220 字: 【会记】会议 20261112-1309-2625（未命名，1:04:34）
 工作区根：`D:\workspace\my_workspace\dsh-note-taker`
 产物文件：`meetings/20261112-1309-2625.md`
 该文件包含元信息、`## 转写` 与 `## 纪要` 两节。…

=== 超长转写 + 无产物 ===
mode=summary chars=33913 消息总长=977
消息前 220 字: …转写共 33913 字 / 641 行，超过单次消息上限（8000 字），
 这里只放开头摘要。[00:00:00] 嗯。 [00:00:02] 啥事儿？…
```

### 两处缺陷

| 编号 | 缺陷 | 表现 |
|---|---|---|
| D1 | summary 模式把 8000 字以上的转写**截成前 800 字**再发 | 用户看到的「只有第一条一句」，长会议必现 |
| D2 | file 模式只给**相对路径** `meetings/<id>.md`，不校验、不给绝对路径 | 会话工作区与产物工作区不同时读不到文件，「没把 md 发给会话」，agent 无内容可总结 |

附带口径不符：发送成功的提示写「（全文，N 字）」，实际可能是 800 字摘要。

### 复现步骤

1. 会记页面 → 历史纪要 → 找一场**没有纪要**的会议（旧会议通常无产物文件）；
2. 点该行「生成纪要」；
3. 看会话里收到的消息：转写超过 8000 字时只有开头摘要；有产物的会议则只有一行路径。
